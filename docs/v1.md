# Tandem × ANDR — v1 Integration Plan

## Goal

Prove one loop end-to-end: a human and two agents coordinate **through the canvas** to plan, approve, and execute a real-world robot action, with the canvas updating to reflect what actually happened.

The demo: *"ANDR, go to the library"* → a planner agent proposes a navigate action on the canvas → the human approves → ANDR executes via Nav2 → the canvas shows the robot moving and the action completing.

This is the thinnest slice that turns Tandem from a **planning** canvas (vitamin) into an **execution/control** surface (painkiller), and it validates the generic execution primitive on the one case that forces it to be real.

---

## Core principles (non-negotiable for v1)

1. **Blackboard coordination, never agent-to-agent chat.** Agents communicate only by reading/writing shared canvas state. The planner writes a proposed action; the executor reads it, runs it, writes status back. No direct messaging between agents — that path reinvents CrewAI/AutoGen and destroys the differentiation.
2. **MCP is the authoring/coordination plane (pull).** Agents author plans and read state over MCP. Robot motion control is **Nav2**, not MCP. Live telemetry in v1 is MCP polling; a websocket is a v2 optimization, not a v1 requirement.
3. **Human approval gates execution.** No action transitions from `proposed` to `executing` without an explicit human approval. This is a safety requirement for a physical robot, not a nicety.
4. **Multi-agent is architecture, not pitch.** It stays invisible plumbing. The user story is "you and your agents run operations on a shared canvas, with approval."
5. **Two agents + human, hard-coded roles.** No general N-agent registration marketplace. Exactly one planner, one executor, one human.

---

## Roles

| Role | Runs where | Owns | Connection |
|---|---|---|---|
| **Planner** | Cloud (strong Claude) | Intent → plan. Resolves the human's goal, proposes the navigate action, reacts to outcomes (re-plans on failure). | MCP client |
| **Executor (ANDR)** | Local, on the Jetson (weak model) | Plan → motion. Reads approved actions, runs Nav2 to compute + follow the path, streams position, reports result. | MCP client |
| **Human** | Browser UI | Approves/rejects proposed actions before anything moves. | Tandem web UI |

The planner/executor split is forced by hardware — the Orin Nano cannot run the planning brain — so this is the only architecture the robot allows, not multi-agent for its own sake.

## What exists today (current MCP inventory)

The `agentcanvas` MCP server (stdio transport) already provides:

**Canvas management**
- `canvas.list`, `canvas.create`, `canvas.select`, `canvas.rename`, `canvas.delete`
- Active canvas is sticky; content tools target it implicitly (no canvas id needed).

**Canvas state / mode**
- `canvas.state.read` — read pins, events, notes, pending edits for the active canvas.
- `canvas.mode.set` — `map` | `itinerary` | `docs`.

**Content (CRUD)**
- Pins: `canvas.pin.add` / `.update` / `.delete` — geographic (lat/lng), `marker`|`annotation`, label, body, color.
- Events: `canvas.event.add` / `.update` / `.delete` — title, start/end (ISO 8601), optional `pinId`.
- Notes: `canvas.note.add` / `.update` / `.delete` — markdown body, optional `parentId`, imageRefs.

**Human ↔ agent loop**
- `canvas.pending_edits.read` / `.complete` — human submits scoped edit requests in the browser; agent reads, applies, marks done.

**Provenance**
- Every entity carries `createdBy` (currently `"agent"` / `"human"`).

**Stack (from repo):** TypeScript + Go + Postgres monorepo, deployed behind Caddy/Docker.

**What this means:** everything today is CRUD on visual entities. There is no concept of an *action*, no execution state, no agent identity beyond agent/human, and no approval handshake for actions. That gap is exactly v1.

## What needs to be built for v1

### 1. New entity: `Action` (the execution primitive)

The single most important addition. It is the unit agents coordinate on and the thing humans approve.

```
Action {
  id: string
  type: "navigate"            // v1 only; extensible later
  state: "proposed" | "approved" | "rejected" | "executing" | "done" | "failed"
  payload: {                  // shape depends on type; for "navigate":
    goalLabel?: string        // e.g. "library"
    goal?: { lat, lng }       // resolved goal pose
    waypoints?: [{ lat, lng }]// optional computed route, shown on map before approval
  }
  proposedBy: string          // agent id (provenance)
  approvedBy?: string         // human/agent id that approved
  result?: string             // execution outcome summary
  error?: string              // failure detail
  linkedPinIds?: string[]     // optional: pins this action references
  createdAt, updatedAt
}
```

**State machine:**
`proposed → approved → executing → done`
`proposed → rejected`
`executing → failed` (planner may then propose a new action = re-plan)

Only the human (UI) performs `proposed → approved | rejected`. Only the executor performs `approved → executing → done | failed`.

### 2. New entity: `Agent` (identity / registration)

Minimal — so the canvas knows who is writing what and provenance is multi-agent.

```
Agent {
  id: string
  name: string
  role: "planner" | "executor"
  model?: string
  status: "online" | "offline"
  lastSeen
}
```

### 3. Waypoints / path

For v1, fold the route into the action payload (`payload.waypoints`) rather than a separate entity. Optionally render waypoints as `annotation` pins so the human sees the actual route before approving. A first-class `Path` entity is a later refinement, not v1.

### 4. New MCP tools

```
agent.register
  in:  { name, role, model? }
  out: { agentId }
  // Agent identifies itself on connect; agentId is used in provenance.

canvas.action.propose
  in:  { type: "navigate", payload, linkedPinIds? }
  out: { id, state: "proposed" }
  // proposedBy = calling agent. Targets active canvas implicitly.

canvas.action.list
  in:  { state? }            // optional filter, e.g. "approved"
  out: { actions: Action[] }

canvas.action.read
  in:  { id }
  out: { action: Action }
  // Executor polls this (or .list with state filter) to detect approval.

canvas.action.approve        // primarily via browser UI; tool included for testing
  in:  { id }
  out: { action: Action }

canvas.action.reject
  in:  { id, reason? }
  out: { action: Action }

canvas.action.update_state   // executor only
  in:  { id, state: "executing" | "done" | "failed", result?, error? }
  out: { action: Action }
```

Position updates reuse the existing `canvas.pin.update` (move ANDR's position pin on a timer).

### 5. Extend existing

- `createdBy` on all entities accepts a registered **agent id**, not just `"agent"`/`"human"`.
- `canvas.state.read` returns `actions` and connected `agents` alongside pins/events/notes.

## ANDR client work (executor side, lives in the ANDR repo)

1. LangGraph agent connects to the Tandem MCP as a client; calls `agent.register({ role: "executor" })`.
2. Poll loop: `canvas.action.list({ state: "approved" })` (or `.read` on a known id) on a timer.
3. On an approved `navigate` action:
   - Hand `payload.goal` / `payload.waypoints` to Nav2's action server (`NavigateToPose` / `FollowWaypoints`).
   - Set the action `executing` via `canvas.action.update_state`.
4. While driving: update the robot's position pin via `canvas.pin.update` on a timer.
5. On arrival → `update_state: done`. On Nav2 failure → `update_state: failed` with `error`.
6. (Optional, better demo/safety) On a freshly *proposed* action, compute the Nav2 path and write `payload.waypoints` back so the human approves the actual route — note: computing a path does not move the robot, so this is safe pre-approval.

---

## Planner client work (cloud Claude, MCP client)

1. Connects to Tandem MCP; `agent.register({ role: "planner" })`.
2. Takes the human's natural-language goal (e.g. "go to the library"), resolves it to a goal (geocode / known-locations lookup), and calls `canvas.action.propose`.
3. Watches outcomes via `canvas.action.read` / `.list`; on `failed`, proposes a new action (re-plan).

**Thinnest-demo collapse:** if standing up a separate cloud planner is too much for the first build, let ANDR's own cloud brain play both roles to prove the loop, then split the planner out as the genuine second agent once `propose → approve → execute → update` works. The architecture is unchanged; only the process count differs.

---

## End-to-end v1 flow

1. Human opens/creates a canvas in `map` mode.
2. Human tells the planner: "ANDR, go to the library."
3. Planner resolves the goal and calls `canvas.action.propose({ type: "navigate", payload: { goalLabel: "library", goal } })`. Canvas shows a **pending** action.
4. (Optional) Executor computes the Nav2 path and writes `payload.waypoints`; the route renders on the map.
5. Human reviews and clicks **Approve** in the browser → action `approved`.
6. Executor's poll picks up the approved action → hands waypoints to Nav2 → sets `executing` → robot drives.
7. Executor updates the position pin on a timer; canvas animates the move.
8. On arrival → `done`. On failure → `failed` + error; planner proposes a re-plan (back to step 3).

Every step is generic — swap "Nav2 path" for "trip itinerary" or "moving-truck route" and the same propose → approve → execute → update loop holds. ANDR is just the forcing function that makes the execution layer real.

---

## Explicitly out of scope for v1

- Agent-to-agent messaging of any kind (coordinate through the canvas only).
- Websocket / push telemetry (v1 polls; websocket is v2).
- More than two agents / dynamic agent marketplace / role discovery.
- Action types beyond `navigate`.
- Multi-tenant auth, billing, conflict resolution beyond last-write-wins.
- Approving the computed path vs. the intent — gate on the action; path-level approval is a v1.5 safety upgrade.

---

## Build sequence (checklist order)

1. **Backend:** add `Action` entity + state machine and `Agent` entity (Postgres migrations, Go services).
2. **MCP:** add `agent.register`, `canvas.action.*` tools; extend `createdBy` to agent ids; include `actions` + `agents` in `canvas.state.read`.
3. **UI:** render pending actions on the canvas with an Approve/Reject control; render the robot position pin and route waypoints.
4. **Executor (ANDR):** MCP client, register, poll-for-approved, Nav2 hand-off, position updates, result reporting.
5. **Planner:** MCP client, register, goal-resolution, propose, re-plan on failure. (Or collapse into ANDR's brain for the first pass.)
6. **Demo:** one mission, end to end, filmed — this is simultaneously the product proof, the ANDR content, and the reference integration.
